## Problem Statement

I have an M5 Unit Synth sitting on my desk. I've already got an Aliro doorkey
running on an AtomS3 with Unit NFC, and Home Assistant orchestrating the house.
I want to do something whimsical with the synth. Bonus curiosity: how close can
a pure MIDI synth get to "speech"?

## What Makes This Cool

The house doesn't talk — it *hums melodies at you*. Each family member gets a
unique wordless leitmotif when they tap in. HA events (weather, packages,
doorbell) trigger short pitched phrases played on Choir Aahs (GM patch 53). It's
ethereal, mysterious, and impossible to explain to a guest without them smiling.

The delight is in the ambiguity. A TTS speaker saying "Bruce is home" is
utilitarian. A cathedral of angels humming a mystery melody when Bruce walks in
is *magic*. Nobody expects a house to sing at them.

Cousin to Vocaloid, Wintergatan, and Speak & Spell — but built on parts that
already work.

## Constraints

- Unit Synth is General MIDI only (SAM2695). No vocoder, no LPC, no actual speech.
- AtomS3 already dedicated to the Aliro doorkey — don't touch its firmware.
- Unit Synth is UART (31250 baud MIDI) — needs its own controller. Confirmed OK
  to use a dedicated AtomS3 Lite.
- Must work through Home Assistant so any HA event can trigger a phrase.
- Audio has to go somewhere — Unit Synth has line-out; needs a small amplified
  speaker or line-in to existing audio.

## Premises

1. The Unit Synth is UART/serial MIDI (31250 baud). Confirmed via M5Stack
   product page for SAM2695 Unit. Dedicated AtomS3 Lite is the right path.
2. A hummed melody per person is more delightful than a spoken name — worth the
   week of tuning to get the melody generator sounding musical, not random.
3. Home Assistant is the right orchestration layer. The synth controller stays
   dumb; HA holds the intelligence (per-person themes, event routing, mood).
4. Choir Aahs (GM patch 53) alone is enough for a first working demo. Layering
   Voice Oohs drone underneath is a v2 polish.

## Approaches Considered

### Approach A: All-on-device
Synth AtomS3 subscribes to MQTT, receives raw text, generates melody locally
from a small syllable-count table, plays MIDI.
- **Pros:** self-contained; no HA dependency for melody logic; simple.
- **Cons:** melody generation is way better in Python than in C++; per-person
  themes and mood logic get gnarly on-device; iterating means reflashing.

### Approach B: HA-brain, synth-dumb *(recommended)*
Home Assistant generates the note sequence (Python has real syllable libs like
`pyphen`, easy to compose per-person themes as YAML). Publishes a MIDI note list
to MQTT. Synth AtomS3 just sequences notes with timing.
- **Pros:** melody logic lives where iteration is cheapest; per-person themes
  are HA templates; the synth controller is 50 lines of C++ that never needs to
  change again.
- **Cons:** requires HA broker running (already the case); slightly more MQTT
  chatter per event.

### Approach C: Multi-voice orchestration *(v2)*
Multiple MIDI channels — melody on channel 1 (Choir Aahs), sustained drone on
channel 2 (Voice Oohs), occasional counter-melody on channel 3 (Synth Voice).
Actually feels like a *piece of music*, not a hum.
- **Pros:** genuinely musical output; distinct events sound like real
  compositions instead of ringtones.
- **Cons:** bigger scope; only worth building after v1 is proven addictive.

## Recommended Approach

**Approach B (HA-brain, synth-dumb) for v1. Upgrade to C once you're addicted.**

The synth AtomS3 becomes a network-callable MIDI player: subscribes to
`home/synth/play`, receives a JSON note list `{"program": 52, "notes": [{"n":
60, "dur": 300}, ...]}`, plays it. That's it. Never needs to be reflashed.

All melody generation, per-person themes, event routing, and mood logic lives
in HA. Change themes by editing a YAML file, not by touching firmware.

**MIDI on SAM2695 — the bytes you actually need:**
- Program change to Choir Aahs: `0xC0 0x34` (GM patch 53, 0-indexed = 52 = 0x34)
- Note on: `0x90 <note> <velocity>`
- Note off: `0x80 <note> 0x00`

**Melody generator (Python side, in HA):**
- Syllable count via `pyphen` (or crude vowel-cluster split)
- Root note = hash(name) → scale degree in C-major
- Cadence: statements descend at the end, questions rise (check final punctuation)
- Per syllable: small random walk within the scale, ±3 degrees, seeded by
  event-type so the same person always sounds *recognizable*
- Duration: 200–400ms per syllable, final syllable slightly longer
- Emphasis: two-note melisma on stressed syllables (v2)

**First working demo:** Any door open → 2-note "hello" phrase on Choir Aahs.
Once that works, add per-card themes.

## Open Questions

- **Speaker choice.** Line-out from Unit Synth into: existing home audio via
  short cable? Small powered desk speaker? M5 Speaker 2 Unit? Depends on where
  the box lives.
- **Latency budget.** MQTT → HA generates → publishes → AtomS3 parses → plays
  should be under 200ms for the door-open case. Test before locking in.

## Success Criteria

- Anyone can flash a fresh AtomS3 Lite from Chrome via the installer page —
  no terminal, no PlatformIO, no clone. This is the door to sharing the
  project with anyone.
- Door opens → within 200ms, house hums a 2-syllable Choir Aahs phrase. Feels
  immediate.
- Each family member has an audibly distinct theme (blind test: someone else in
  the house guesses who just tapped in).
- Adding a new theme is a HA YAML edit, not a code change.
- At least one guest asks "wait, did the house just *sing*?" within the first
  week.

## Distribution Plan

**Flash-from-browser via ESP Web Tools**, following the pattern established by
the Aliro doorlock project (`~/Development/aliro-doorlock-esp32/`). Non-negotiable
baseline — a friend or family member should be able to open a URL, click Connect,
and have a working humming-house device without installing PlatformIO or opening
a terminal.

Repo: **singing-oracle-esp32** — matches the `<product>-esp32` pattern from
`aliro-doorlock-esp32` and `HomeKey-ESP32`.

Layout to mirror:
- `installer/index.html` — ESP Web Tools embed page (customized UI, links to
  manifest.json, post-flash setup flow for WiFi + MQTT broker credentials).
- `installer/js/` — modules for whatever post-flash setup this device needs.
  For the Singing Oracle: `setup-flow.js` (WiFi + MQTT broker fields),
  `serial-monitor.js` (see boot logs in the page), `install-controller.js`
  (orchestrate flash → configure → verify). Skip matter-payload, qr-render,
  device-protocol — those are Matter-specific.
- `installer/vendor/esp-web-tools/` — vendored as git submodule (same as Aliro).
- `installer/tests/` — carry over the test harness pattern. Boot-parser and
  setup-flow tests especially.
- `artifacts/singing-oracle-vX.Y.Z-atoms3lite/` — versioned per-release
  directory containing `*-factory.bin`, `*-app.bin`, `*.bin.sha256`, and
  `manifest.txt` describing partition layout and OTA slots.
- `.github/workflows/deploy-installer.yml` — CI that builds firmware, generates
  the ESP Web Tools `manifest.json`, and deploys the installer to GitHub Pages
  on every tag.
- `installer/README.md` — dev docs.

The manifest.json that ESP Web Tools consumes is generated at deploy time from
the artifacts directory, not hand-maintained. Aliro's workflow already does
this — read `.github/workflows/deploy-installer.yml` there and adapt.

HA side is still a YAML snippet copied into `configuration.yaml`. That side
doesn't need an installer.

  have working* (Aliro doorkey, HA, one specific unit on the desk). That's the
  right way — most people brainstorm in a vacuum and end up with ideas that

- When I described the speech options, you didn't chase the impressive one. You
